# 操作者体验

> **这份文档回答: 用户打开页面后看到什么, 以及为什么是这样设计的。**
>
> 相关: [`unattended-operation.md`](unattended-operation.md)(机器做什么)、
> [`../architecture.md`](../architecture.md)(内部怎么实现)。

---

## 1. 唯一的产品原则

```
结论 > 原因 > 影响 > 系统动作 > 用户动作
```

而不是:

```
技术字段 > 状态码 > 日志 > 用户自己判断
```

举例 —— 同样是「权益漂移」这件事:

❌ **错误**
```
equity_drift = 0.032
reconcile_killed = true
```

✅ **正确**
```
系统已暂停交易

原因: 账户资产与系统预期存在 3.2% 差异。
系统动作: ✓ 已暂停买入 ✓ 已暂停卖出 ✓ 正在重新同步 Binance ✓ 已完成 2 次自动对账
用户动作: 暂时无需操作
```

这条原则由 `at01_common/operator_narrative.py::explain()` 落地: 它输出**固定五段式**,
任何内部状态都必须能填满这五段(有测试穷举 7×10×5 种状态组合断言非空)。

---

## 2. 首屏: 5 秒内知道系统是否正常

页面第一屏(`/`)依次是:

```
[系统运行正常]  [无人值守运行中]
模拟运行中。系统运行正常, 无需操作。

原因 / 影响 / 系统动作 / 你需要做什么 / 下一步

模式: 模拟   交易: 允许买入   账户权益: ¥99,395   今日收益: 今日无交易
────────────────────────────────────────────
🩺 系统状态        系统正常, 无需操作。
📜 今天发生了什么   最近 N 条
🧾 今日系统复盘     今天还没有交易。
🔔 最近需要你关注的事情
🛑 立即停止交易
```

**没有问题时只给一句话。** 任务书明确要求: 「不要显示一堆绿色 PASS」「如果用户不需要
做任何事情, 明确告诉用户无需操作」。所以「系统状态」卡在全部正常时只渲染一行
`✓ 系统正常, 无需操作。`

**技术指标不在第一屏。** 行情/分析/风控/持仓等卡片仍在页面上, 但排在结论之后 ——
需要深挖时才往下看。

## 3. 三模式, 不是四个布尔量

界面上只有:

```
模拟  ── 本地模拟成交, 不产生任何真实订单
测试  ── Binance 测试网真实下单(假钱)
实盘  ── Binance 主网真实资金
```

**行情数据源与模式正交**, 不是第四种模式: 测试网行情稀薄, 想看真实流动性可以用
「模拟 + 主网行情」。它是高级选项(`advanced` 字段), 不在首屏。

不暴露给用户的内部词汇:
`paper_testnet` / `live_testnet` / `live_mainnet` / `paper_mainnet` /
`PAPER_TRADING` / `BINANCE_TESTNET` / `RUN_TESTNET_TRADING` /
`LIVE_TRADING_CONFIRM` / `MAINNET_API_SCOPE_CONFIRMED`。

它们仍可在**高级诊断**里看到(`/ops` 的折叠区)。判定与推导在
`at01_common/trading_mode.py`; 单一权威仍是 `TRADING_MODE`, 旧字段由它推导。

> 唯一例外: **部署配置文件里的环境变量名**必须照实写(`BINANCE_TESTNET_API_KEY` 等)——
> 用户真的要去填它们, 藏起来反而让他无从下手。

## 4. `/admin` — 管理控制台

改配置 / 切模式 / 管理操作。

**配置以数据库为权威**(V12.6 起): 写的是 `runtime_config` 表, 优先级 `DB > env > default`。
配置文件只用于三件事: 显示「文件值 vs 运行值」差异、回滚来源、密钥与 bootstrap 键
(密钥**绝不入库**)。

保存成功后提供**「自动重启并验证」**: 页面会逐项打勾(配置验证 / 服务重启 / 数据库 /
行情连接 / 风控 / 对账), 用户不需要自己 `docker restart` + `curl` 确认。
详见 §6。

## 5. `/setup` — 一键进入无人值守

首次配置只需要确认**五件事**:

```
✓ API Key / Secret      ← 模拟模式不需要(只读公开行情)
✓ 交易模式              ← 三选一
✓ 资金与风控边界         ← 只列 5 项关键边界, 其余用推荐默认值
✓ 策略版本              ← 启动时自动冻结基线
✓ 真实资金运行确认       ← 仅实盘必需, 必须人工
```

页面**只读**: 没有任何写路径, 也不提供绕过守卫的入口。写仍走既有通道
(`/api/trading-mode/*`、`/api/admin/config/*`), 高风险动作在那边照旧需要显式确认。

五项齐备后页面给出「系统已进入无人值守运行」+ 现场事实(模式/标的/权益/风险等级/
买卖许可/策略版本/最近对账/系统健康)。

## 6. `/ops` — 系统健康报告

**不是**「部署考试页面」, **不是**「用户需要逐项检查的清单」。

页面先给结论(「系统正常, 无需操作」或「需要你的确认: …」), 只有**异常项**才展开
技术细节; 技术细节整体收进默认折叠的「高级诊断」。

每个检查项都标明**归谁管**(任务书 P0 的 A/B/C 三分类):

| 标记 | 含义 |
|------|------|
| 系统自动处理 | 系统自己会恢复, **不打扰用户** |
| 系统自动阻止交易 | 系统自己会停手, **无需人工确认** |
| 需要你的确认 | 必须人来做 |

> **观察指标不参与结论**: 订单失败率是喂给 AI 复盘的观察项 —— 一笔订单没成交不代表
> 系统不正常。若把它算进总结, 页面会在一切正常时显示「系统正在自动处理」,
> 那是**虚报异常**, 与「无事就明说无需操作」直接冲突。实现见
> `web_health_report.py` 的 `blocking` 字段。

## 7. 日志产品化

**技术日志仍然存在**(`logs/adaptive.log`, 服务开发者, 回答「为什么发生」);
页面展示的是**操作员事件流**(服务操作者, 回答「发生了什么」):

```
14:32:01 系统启动
14:32:03 行情数据源已连接(Binance 主网)
14:32:10 账户同步与对账完成, 系统进入就绪
14:35:21 发现 BUY 信号(decision)
14:35:21 风控通过
14:35:22 BUY 订单已提交
14:35:23 BUY 已成交 @ 102.10
14:35:23 BUY 交易完成
```

用户**不需要** `docker compose logs | grep`。

事件流的两条实现约束(`at01_common/operator_events.py`):

- `emit()` **同步且永不抛异常**: 先写内存环, 再 best-effort 落库 —— 事件流故障
  不得影响交易主链路;
- **脱敏是硬约束**: 事件会进日报与 AI 复盘包, 所有字符串按 `NAME_KEY=value` 形态
  二次扫描(密钥常被拼进自由文本, 只按键名过滤会漏)。

降噪: 只对「高频且重复本身不含信息」的 kind(信号/风控拦截)做连续合并计数;
**稳定性计数用的 kind 一律不去重** —— 「今日 3 次重连」必须真的是 3,
合并成 1 会让日报低报故障频次。

## 8. 交易结论可解释

每笔交易生成一条人话结论(`operator_narrative.explain_trade`):

```
BUY SOLUSDT   结果: 成功   价格: $102.10   数量: 3.0 SOL
为什么买: 市场状态 TRENDING / 趋势 上升 / 资金流 正向 / 策略评分 86
风控: 单笔风险正常 · 日亏损正常 · 账户敞口正常
执行: 订单 FILLED · 滑点 0.12% · 耗时 340ms
```

返回**结构化字段 + 预渲染标题**, 而不是一段纯文本 —— 纯文本没法被程序再消费,
未来 AI 要直接读它。

## 9. 页面清单

| 路径 | 定位 | 写操作 |
|------|------|:------:|
| `/` | 首屏结论卡 + 系统状态 + 事件流 + 今日复盘 | 仅急停/恢复/熔断/停机 |
| `/setup` | 一键进入无人值守(五要素核对) | ❌ 只读 |
| `/admin` | 配置 / 模式 / 管理操作 | ✅ 需令牌 |
| `/ops` | 系统健康报告(结论优先) | ❌ 只读 |

**无任何下单端点。** 急停/恢复也只调风控既有接口。
