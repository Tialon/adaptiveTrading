# 无人值守运行

> **这份文档回答一个问题: 系统跑起来之后, 到底还需要人做什么?**
> 逐类列清「机器做 / 机器自动恢复 / 需要人 / 绝对不需要人」。
>
> 相关: [`operator-experience.md`](operator-experience.md)(页面怎么看)、
> [`../ai-review-spec.md`](../ai-review-spec.md)(复盘包格式)。

## 1. 四类事项(单一来源)

分类收口在代码里的一处: `at90_web/web_health_report.py` 的 `HANDLING_*`。
页面据此决定要不要打扰用户 —— 不各处各判一套。

| 类别 | 含义 | 打扰用户? |
|------|------|:---------:|
| `AUTO` | 系统自动处理 | ❌ |
| `AUTO_BLOCK` | 系统自动阻止交易, 服务继续运行 | ❌ |
| `HUMAN` | 必须人工确认 | ✅ |

### 1.1 机器做(不需要人)

启动自检 · 连接交易所 · 行情预热 · 账户同步 · 对账 · 策略评分 · 下单执行 · 记账 ·
每日复盘 · AI 复盘包生成。

### 1.2 机器自动恢复(不需要人)

| 情形 | 处理 |
|------|------|
| 网络失败 / API 超时 | 重试 + 退避 |
| WS 断线 | 自动重连 |
| 数据延迟 / 静默 | 暂停开仓, 等数据恢复 |
| 瞬态对账差异 | 下个周期重新对账 |
| 关键后台任务崩溃 | **有界自动重启**(指数退避, 默认 3 次), 期间禁开仓 |
| 风险态 PAUSED | 窗口到期自动恢复 |
| 熔断器打开 | 冷却后自动复位 |
| 生命周期 DEGRADED / RECOVERY | 对账 PASS 后自动回升 |

原则: **系统宁可自己停, 也不要要求用户不断看守。**

### 1.3 需要人(必须确认)

| 事项 | 为什么必须是人 |
|------|----------------|
| 进入主网真实资金 | 动真钱, 责任在人 |
| 修改核心风控参数 | 改风控阈值就是改交易行为 |
| 激活新的策略版本 | AI 只产 proposal, 激活是人的判断 |
| 解除**人工**急停 | 人按的按钮, 由人 unpin |
| 解除**重大资金异常**急停 | 见 §3「无法自证」 |
| 改变资金规模 | 风险偏好是人的选择 |
| 关键任务**重启额度用尽**后恢复 | 反复崩溃说明有系统解决不了的问题 |

### 1.4 绝对不需要人

读日志 · 手工对账 · 手工重启任务 · 手工判断系统是否健康 · 重启服务恢复普通故障 ·
理解 `PAPER_TRADING` / `BINANCE_TESTNET` / `RUN_TESTNET_TRADING` 这些内部开关。

## 2. 自动恢复的边界(本系统最重要的安全设计)

任务书同时要求两件方向相反的事:

```
KILL → 自动进入 RECOVERY_CHECK → 重新连接 → 重新对账 → … → 全部正常 → 自动恢复
对「人工主动 KILL」与「重大资金异常 KILL」保留人工恢复确认
```

判据是**能否自证**: 自愈的前提是「条件已恢复」这件事**系统能自己证明**。

| 冻结来源 | 自愈 | 理由 |
|----------|:----:|------|
| `MANUAL`(人工急停 / 启动守卫拦截) | ❌ | 人按的按钮 |
| `AUTO_TASK`(关键任务崩溃) | ✅ | 任务跑起来就是自证 |
| `AUTO_DATA`(行情失真) | ✅ | 数据校验通过就是自证 |
| `AUTO_EQUITY`(回撤 / 权益异常) | ❌ | **无法自证** |
| `AUTO_ACCOUNTING`(本地记账失败) | ❌ | **无法自证** |
| `AUTO_RECONCILE`(对账矩阵 KILLED) | ❌ | **无法自证** |
| 来源为空 / 无法识别 | ❌ | fail-closed |

**为什么「无法自证」是硬边界**: 这三类都代表**账本与真实资产对不上**。重新对账只是
拿自己的账本对自己的账本 —— 在账本本身可疑时, 「已经对上」这个结论没有意义。
只能由人核对 Binance 账户。

实现: `at50_risk/auto_recovery.py`(判定与编排)+ `at50_risk/recovery_flow.py`(恢复动作)。
**人工与自动共用同一段恢复代码**, 否则迟早出现「人工能恢复、自动恢复不了」这类
最难排查的不一致。

自动恢复带**指数退避**(30→60→120s)与**尝试上限**(默认 5 次); 用尽后升级为
「需要人工」并**停止空转** —— 反复失败还一直重试, 等于让用户对着一个不会有结果的页面等。

## 3. 恢复流程

```
冻结
 ↓
自动恢复协调器 / 人工点「恢复急停」
 ↓
前置条件核对(全部读 TradingGate 的既有健康位, 不另起一套判定)
   连接正常 · 行情健康 · 交易所可信 · 对账通过 · 关键任务在跑
 ↓ 不满足 → 原地不动, 如实说明还差什么
 ↓ 满足
逐层解开: 急停 → 风险态(KILLED→RECOVERY_CHECK→NORMAL) → 生命周期(SAFE_MODE→READY→TRADING)
 ↓
恢复完成 —— 但**能否下单仍由闸门逐笔判定**
```

> **解冻 ≠ 允许下单**。恢复流程不写 `can_buy`, 也不碰任何风控维度。

### 3.1 「恢复急停」= 恢复检查, 不是清除 KILL

V15 起 `POST /api/emergency/recover` 的语义是**请求系统重新做一遍安全检查**, 而不是
「把冻结标志清掉」:

```
解除人工急停 (仅此一步是"清标志")
  ↓
逐项复检: 停机窗口 / 行情 / 交易所账户 / 对账 / 关键任务 / 配置
  ↓
全部满足 → 恢复 TRADING
任一不满足 → 保持冻结 + 逐项告诉用户「是谁在挡、为什么、能不能自证、要不要人」
```

条件分三类, 决定人工确认能否越过:

| 类别 | 例 | 人工确认可越过? |
|------|----|:---------------:|
| `account_truth` | 交易所账户 / 资金 / 持仓 / 现金 / 对账 | ✅ 操作者明确表示已核对账户 |
| `self_healable` | 行情不可信 / 关键任务不在 | ❌ **等它自己恢复** |
| `blocking` | 停机窗口 / 配置非法 | ❌ 改配置或重启 |

> **为什么行情不可信时连人工确认也不放行**: 越过了就等于在数据不可信时下单 ——
> 确认解决不了这个问题。这类只能等系统自己恢复。

实现: `at50_risk/recovery_flow.py`。**不放宽任何判定** —— 读的全是 `TradingGate`
已有健康位与既有 `validate()`; 有 AST 测试断言模块里不存在 `force_normal`
或给 `can_buy` 赋值之类的捷径。

## 4. 通知分级

页面按五档决定要不要打扰用户(`at01_common/operator_narrative.py`):

| 级别 | 含义 | 用户要做什么 |
|------|------|--------------|
| `NORMAL` | 一切正常 | 无 |
| `NOTICE` | 值得记录, 能力未降级 | 无 |
| `DEGRADED` | 能力下降, **系统正在自动恢复** | 无 |
| `ACTION_REQUIRED` | 真正需要人 | 按页面说明操作 |
| `KILLED` | 交易已冻结 | 视来源: 自愈中 or 需要确认 |

**「无需操作」是有依据的**: 只有系统真的会自愈的状态才会这么说。
`SAFE_MODE` 在 V13 之前没有自动退出路径, 所以当时的文案如实写成需要人 ——
不谎称自愈。这类状态一旦接入自动恢复, 文案才跟着改。

## 5. 急停

### 5.1 自动急停

严重权益异常 · 严重对账异常 · 数据源失真 · 关键任务连续失败 · 未知订单状态 ·
账户状态无法确认 —— 系统自动冻结、记录原因、保留证据、进入恢复循环。
**用户不需要立即操作。**

### 5.2 人工急停

页面上一个显眼的「立即停止交易」按钮, **点击立即生效, 不做二次确认**。
冻结是安全方向, 应即时可用(架构文档亦如此规定)。

### 5.3 永久性

急停状态**持久化**(`kill_switch_state` 表), 重启进程不会自动解除。

## 6. 关键任务自动重启

`at01_common/runtime_supervisor.py`

```
critical 任务异常退出
 ↓
标记缺席(立刻禁开仓) ← 重启要退避等待, 那段时间监控并没有在跑
 ↓
指数退避重启(默认 3 次)
 ↓ 成功 → 任务回来, 全部关键任务在位则恢复开仓许可
 ↓ 额度用尽
冻结 + SAFE_MODE + 急停(与 V13 之前的行为逐字一致)
```

**没有降低最终安全等级**: 重启额度用尽后行为不变; 未配置重启工厂时行为也不变。

> ⚠️ 「任务缺席」与「已冻结」是**两个独立状态**。旧契约下 critical 任务一崩就冻结,
> 所以「冻结」恰好等价于「任务不在」。有了重启就出现一段任务缺席的窗口 —— 那段时间
> 必须禁开仓, 否则等于**在监控缺失的情况下继续交易**。

---

## 7. 仍然需要人值守的场景(诚实披露)

- **重启额度用尽**: 关键任务反复崩溃, 说明有系统解决不了的问题;
- **重大资金异常冻结**: 必须人核对交易所账户;
- **主网真钱上线**: 本系统**不自行批准**首笔主网真实交易;
- **进程在容器外退出**: 没有 `restart: unless-stopped` 就不会自动拉起。

这四条是**设计如此**, 不是缺口。
